## What the delta does establish (source-level)

- **Child-local, pre-`main` pin.** `command()` and `boundedCommand()` set `cmd.Env = childEnvironment()` — a non-nil, single-entry slice — so `exec.Cmd` does **not** inherit the parent block; the value is present at `execve` and therefore before `parsedebugvars`, which per the supplied `runtime/cgroup_linux.go` precedes `defaultGOMAXPROCSInit`. With `debug.containermaxprocs == 0` the `else` path runs `c.Close()` (lines 45–71), so no CPU-limit descriptor survives into `main`. The reasoning that `GOMAXPROCS` alone is not equivalent is correct against this source.
- **Exact and non-shared.** `childEnvironment()` returns a fresh literal each call; `TestChildRuntimeSettingExact` pins both the literal and `cmd.Env`/`cmd.Environ()`, and pins non-aliasing of the returned slice. It starts no process (`CommandContext` only constructs), so purity is preserved.
- **Bound into the frozen plan, drift refused.** `plan.ChildEnvironment` is emitted by `freeze()`, carried in the digested plan file, decoded under `strictJSON` (unknown-field rejecting), and re-derived-and-compared in `validateChildLaunch`, which `validatePlan` now calls on both the freeze and `execute-reviewed` paths. `TestChildLaunchRefusesOverridesAndDrift` genuinely refuses nil/empty, `GOMAXPROCS`-only, flipped value, appended GODEBUG sub-setting, duplicate entry, and extra `PATH=` — and, per case, a mutated or duplicated `--setenv GODEBUG` in argv. The old inline argv `DeepEqual` loop is preserved inside `validateChildLaunch`, not replaced by a weaker check, and the `len(value.Argv) != len(cases)` guard plus per-case equality closes missing/extra keys.
- **W path.** `writerArgv` inserts `--setenv GODEBUG containermaxprocs=0` **after** `--clearenv` (correct bwrap ordering) and before the binds; no `--preserve-fds`, no `*-try`, no root bind, no `--unshare-time`, no new mount, no privilege change. The intervening `ld.so`/bwrap hops are non-Go, so the pin only has to survive to `/writer`, which it does through bwrap's own env construction rather than inheritance.
- **No weakening elsewhere.** `fdInventory` is byte-identical to R2 (fd>2 still refused; only the pre-existing eventpoll/eventfd allowance; nothing closed, nothing allowlisted). Namespaces, pipe custody, frame bounds, deadlines, lease/version/commit checks, retention and `validate-result`'s exit-0 precondition are untouched. `runner_linux.go` changes only the transaction label; `README.md` is documentation. The negative build log (`offline-red.txt`) shows the two new tests fail to compile against the pre-delta symbols, so they are bound to the real new symbols and are not vacuous. Reuse of the R2 SOURCE PASS for the byte-identical files listed in both manifests is legitimate as far as I can check the two manifests against each other.

## Must-fix

**M1. The causal premise — that the rejected fd 3 `/sys/fs/cgroup/init.scope/cpu.max` was opened by V's own runtime rather than inherited across `execve` from the runner — is neither established by the supplied evidence nor defended by any check in the delta. If it is wrong, the entire R3 correction is inert, and it will fail in exactly the same undiagnosable way.**

The supplied `runtime/cgroup_linux.go` proves *when* the descriptor is opened and that `containermaxprocs=0` closes it **in the process that parses that GODEBUG**. It says nothing about `O_CLOEXEC` on the descriptor. `internal/runtime/cgroup/cgroup_linux.go`, the only file that determines whether the runner's own retained CPU-limit descriptor survives `execve` into V, is cited **by hash only**; its content is not in the payload, so I cannot verify the open flags. The runner (`execute-reviewed`) is itself a Go 1.26.7 process, started with the ambient host environment and therefore *without* the pin, and it retains such a descriptor for its lifetime. `os/exec` does not close non-`CLOEXEC` inherited descriptors in the child; it only installs `Files`/`ExtraFiles`. The R2 observation does not discriminate the two hypotheses: V was launched with no `ExtraFiles`, so an inherited descriptor and a self-opened one both land at the lowest free number, 3. The R2 reassessment's rebuttal ("empty Env/no inherited `ExtraFiles` for V") addresses argument passing, not descriptor inheritance, and `GODEBUG` on the child cannot close a descriptor the child's runtime never opened.

Two things are required, and both are source-level and in scope:

1. Quote the actual `OpenCPU`/open call sites from the installed `internal/runtime/cgroup/cgroup_linux.go` (hash `9f192b1…`) showing the `O_CLOEXEC` flag on every descriptor retained past `defaultGOMAXPROCSInit`. If `O_CLOEXEC` is absent, R3 as written is not a fix and must not be executed.
2. Independently of (1), add a closed check on the runner side so this failure mode is attributed rather than silently repeated: at the top of the `execute-reviewed` path, before any child is created, enumerate the runner's own `/proc/self/fd` and **refuse** (INCONCLUSIVE, with the link target in the error) any descriptor >2 that is not a permitted runner-owned kind. Do **not** close it, do not allowlist it, do not relax `fdInventory`. This is the only construct that turns "the pin was inert because the surface was inherited" into a first-class, attributed refusal at the parent, and it also converts the current unverified premise into an executable discriminator.

Re-review scope after M1: the added runner precondition and its pure test, plus regenerated `source.sha256` and plan digest. The rest of this delta needs no further source work at this scope.
